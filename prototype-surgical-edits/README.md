# Прототип — выброшенный код (issue #10)

Первоисточник для находок, зафиксированных в резолюции
[issue #10 «Хирургические правки: путь в схеме ↔ диапазон текста»](https://github.com/crystallpunk-14/SS14Editor/issues/10).
Не переносится в продакшн как есть. Библиотека и подход (CST-слой `yaml`@eemeli как оракул
позиций) — по решению [issue #3](https://github.com/crystallpunk-14/SS14Editor/issues/3).

## Что здесь есть

- `lib/model.mjs` — парсинг (`parseDocument` c `keepSourceTokens: true`, `LineCounter`) и
  разрешение пути «entity → компонент по `type:` → поле» в узел AST.
- `lib/edits.mjs` — все три класса правок из тикета плюс удаление ключа/компонента.
- `lib/diff.mjs` — вывод настоящего unified diff (`git diff --no-index`) и re-parse-проверка,
  что результат правки остаётся валидным YAML.
- `demo-fireaxe.mjs` — обязательная часть тикета: три класса правок на реальном
  `fixtures/fireaxe.yml` (1:1 копия `Resources/Prototypes/Entities/Objects/Weapons/Melee/fireaxe.yml`
  форка `crystall-edge`).
- `demo-hazards.mjs` — побочные вопросы карты на реальных фикстурах из того же форка:
  `fixtures/job.yml` (`StatusIcon/job.yml` — якоря/алиасы, комментарий перед НЕ-первым
  элементом списка), `fixtures/light.yml` (`_CE/Procedural/Demiplane/Modifiers/light.yml` —
  `!type:`-тег), `fixtures/memorial.yml` (`Entities/Structures/Furniture/memorial.yml` —
  блочный скаляр `description: |`).
- `demo-comment-insertion.mjs` — резолюция issue #14: вставка (классы 2 и 3) рядом с
  комментарием, прилипшим к последнему существующему полю/компоненту. Фикстуры:
  `fixtures/mapping.yml` (`Actions/mapping.yml` — трейлинг-комментарий на той же строке),
  `fixtures/alert_levels.yml` (`AlertLevels/alert_levels.yml` — standalone многострочный блок
  после последнего поля плоской карты), `fixtures/drinks_bottles_plastic.yml`
  (`Entities/Objects/Consumable/Drinks/drinks_bottles_plastic.yml` — standalone комментарий
  после последнего компонента `components:`, паттерн повторяется 13 раз в одном файле). Разбор
  — `docs/research/yaml-insertion-near-comments.md`.
- `demo-nested-materialization.mjs` — резолюция issue #16: класс 4, материализация ВСЕЙ
  отсутствующей цепочки контейнеров разом (не только последнего ключа, как класс 2). Фикстура
  — уже существующая `fixtures/fireaxe.yml`: `FireAxeFlaming.MeleeWeapon` не упоминает `damage`
  вовсе (наследуется от родителя `FireAxe`), путь `damage.types.Piercing` отсутствует в тексте
  на всю глубину.
- `demo-toplevel-seq-comment.mjs` — резолюция issue #17: кому принадлежит комментарий перед
  САМЫМ ПЕРВЫМ элементом top-level последовательности прототипов (документ без обёртывающего
  ключа, в отличие от `components:`). Фикстуры: `fixtures/types.yml` (`Actions/types.yml` — 43
  entity, две комментарные группы перед первым entity, разделённые пустой строкой),
  `fixtures/substation.yml` (`Entities/Structures/Power/substation.yml` — контрольная фикстура:
  тот же top-level-эффект перед первым entity ПЛЮС комментарий перед первым компонентом
  вложенного `components:`, в одном файле). Разбор —
  `docs/research/top-level-seq-leading-comment.md`.

Запуск: `npm install`, затем `node demo-fireaxe.mjs`, `node demo-hazards.mjs`,
`node demo-comment-insertion.mjs`, `node demo-nested-materialization.mjs` и
`node demo-toplevel-seq-comment.mjs`.

## Ответы

### Путь в схеме → диапазон текста

Путь — `{ entityIndex, component, fieldPath }`.

- **Entity** внутри top-level последовательности прототипов адресуется **позиционным
  индексом**. Стабилен на время жизни одного открытого документа: узел дерева инспектора и
  так пересоздаётся целиком при любом внешнем изменении текста (см. ниже), так что индекс не
  «протухает» тише, чем весь документ.
- **Компонент** внутри `components:` адресуется **значением поля `type:`, не индексом**.
  Причины: (1) движок не допускает двух компонентов одного типа на одной entity — `type`
  уже уникальный ключ внутри списка; (2) индекс рассыпается при вставке/удалении СОСЕДНЕГО
  компонента в том же редакторском шаге, а `type` — нет; (3) мерженный (с учётом наследования)
  список компонентов, который видит UI, не обязан совпадать по порядку с сырым списком в
  файле — только `type` согласован по обе стороны.
- **Поле** — обычный спуск по ключам (`fieldPath: string[]`, поддерживает вложенность вроде
  `damage.types.Blunt`).

Разрешение пути даёт либо диапазон существующего скаляра (`node.range` — абсолютные
char-офсеты, `LineCounter.linePos()` переводит в `{line, col}` для `vscode.Range`), либо
контейнер без искомого ключа (см. класс 2).

### Три класса правок (`demo-fireaxe.mjs`, на `fixtures/fireaxe.yml`)

1. **Замена скаляра на месте.** `pair.value.range` — точный диапазон значения без хвостовых
   пробелов/комментариев. Правка — `text.slice(0,start)+new+text.slice(end)`. Диффнута ровно
   одна строка (`Sprite.state: icon → icon-open`).
2. **Материализация унаследованного поля.** У `FireAxeFlaming.MeleeWeapon` в файле нет
   `attackRate` — оно наследуется от родителя. Точка вставки — граница `range[2]` последнего
   существующего поля контейнера: офсет, с которого начинается СЛЕДУЮЩИЙ токен вообще (что бы
   там ни было — соседнее поле, отступ следующего элемента списка), гарантированно вне
   диапазона всех соседей. Отступ — колонка первого соседнего ключа того же контейнера
   (`LineCounter.linePos(...).col`): в блочных картах SS14 все поля одного узла всегда на
   одной колонке. Диффнута ровно одна новая строка.
3. **Добавление целого блока `- type: X` в `components:`.** Тот же приём с `range[2]`
   последнего элемента списка. Отступ считается в двух частях: колонка первого поля первого
   существующего компонента даёт колонку ПОЛЕЙ нового блока; тире — на 2 колонки левее (в
   блочной последовательности `- ` перед первым ключом съедает ровно 2 колонки — эмпирически
   подтверждено на реальном файле, не предположение). Диффнуты ровно три новые строки.

Success-критерий тикета («дифф трогает только целевые строки») выполнен на реальном файле для
всех трёх классов — см. вывод `demo-fireaxe.mjs`. Каждый результат дополнительно проверен
чистым re-parse (`lib/diff.mjs:assertReparsable`) — правка не просто выглядит как чистый diff,
она остаётся валидным YAML.

### Удаление ключа/компонента и «прилипшие» комментарии (`demo-hazards.mjs`)

Нетривиальный и неочевидный факт архитектуры `yaml`@eemeli, обнаруженный эмпирически:
**комментарий перед ПЕРВЫМ элементом коллекции (карты или списка) в CST принадлежит не
элементу, а контейнеру** (`containerNode.commentBefore`), и у первой пары карты `.start`
пуст — даже её собственный отступ на той же строке никому не принадлежит как диапазон.
Для НЕ-первых элементов komментарий/пустые строки/отступ — это `.start`-токены ИМЕННО этого
элемента, с точным офсетом, который эмпирически всегда равен `range[2]` предыдущего соседа
(инвариант проверен и на картах, и на списках, в двух разных файлах).

Отсюда — два разных правила удаления, оба реализованы и продемонстрированы на реальных
файлах:

- **Удаление первого ключа карты** (`typesMap` → `Blunt` в `fixtures/fireaxe.yml`,
  комментарий `# axes are kinda like sharp hammers...` висит на контейнере): комментарий
  остаётся на месте, удаляется только своя строка ключа. Правильная граница начала —
  начало СТРОКИ первого ключа (текстовый откат до последнего `\n`), а не `key.range[0]`:
  голый `key.range[0]` не включает собственный отступ пары, что на реальном прогоне дало
  задвоенный отступ у следующего ключа — баг найден и исправлен именно на этой фикстуре,
  не в вакууме.
- **Удаление НЕ-первого элемента списка** (`fixtures/job.yml`, `# Cargo` перед
  `JobIconCargoTechnician`): комментарий уходит вместе с элементом — `.start[0].offset`
  уже точно указывает на конец предыдущего элемента.

**Проверено в issue #17** (было открытым вопросом здесь): комментарий прямо перед САМЫМ первым
элементом последовательности — см. отдельную секцию ниже, ответ оказался НЕ симметричен правилу
для карт.

### Вставка (классы 2 и 3) рядом с комментарием (`demo-comment-insertion.mjs`, issue #14)

Резолюция [issue #14](https://github.com/crystallpunk-14/SS14Editor/issues/14) — единственный
оставшийся открытый вопрос из «Residual unknowns» п.3
[`docs/research/ts-yaml-node-positions.md`](../docs/research/ts-yaml-node-positions.md): куда
именно попадает вставка (класс 2 `insertKey`, класс 3 `insertComponentBlock`), если последнее
существующее поле/компонент контейнера сопровождается комментарием. `fixtures/fireaxe.yml`
этот случай не покрывала вообще — у обеих точек вставки там нет соседнего комментария.

Полный разбор с точными офсетами — [`docs/research/yaml-insertion-near-comments.md`](../docs/research/yaml-insertion-near-comments.md).
Коротко: **трейлинг-комментарий на той же строке, что последнее поле, — безопасен всегда**
(он уже поглощён в `range[2]` значения, наивный и правильный офсет тождественны — доказано
равенством на `fixtures/mapping.yml`). **Standalone-комментарий на отдельной строке — не был
безопасен**: он становится `.comment` самого КОНТЕЙНЕРА (карты или `components:`-seq), а не
последнего элемента, и старый алгоритм (`range[2]` последнего элемента) вставлял новое
содержимое МЕЖДУ последним элементом и его комментарием, отрывая комментарий от того, к чему
он относился (найдено и продемонстрировано на `fixtures/alert_levels.yml` и
`fixtures/drinks_bottles_plastic.yml`, паттерн повторяется 13 раз в одном реальном файле форка).
**Пофикшено** в `lib/edits.mjs`: `insertKey`/`insertComponentBlock` теперь берут `range[2]`
самого контейнера, а не последнего элемента — на уже доказанных no-comment случаях
(`fireaxe.yml`) оба офсета тождественны (проверено, `demo-fireaxe.mjs`/`demo-hazards.mjs` дают
неизменные диффы), так что регрессии нет.

### Материализация вложенных отсутствующих контейнеров произвольной глубины (`demo-nested-materialization.mjs`, issue #16)

Резолюция [issue #16](https://github.com/crystallpunk-14/SS14Editor/issues/16) — компромисс,
явно оставленный открытым в issue #10 (см. «Принятые компромиссы прототипа» выше): класс 2
(`insertKey`) материализует только последний ключ пути и падает с ошибкой, если хоть один
промежуточный контейнер отсутствует в тексте. Реальный случай сидел уже в собственной фикстуре
issue #10 и не потребовал новой: `FireAxeFlaming.MeleeWeapon` вообще не упоминает `damage` —
оно наследуется целиком от родителя `FireAxe`, у которого `damage.types.{Blunt,Slash,Structural}`
задано текстом. Путь `damage.types.Piercing` у потомка отсутствует на глубине 0 (нет даже
`damage`) — ровно пример из тела тикета.

**`findField` меняет контракт**: вместо исключения на первом отсутствующем промежуточном ключе
теперь всегда возвращает `{ container, pair, missingPath }`, где `missingPath` — весь хвост
пути, которого нет в тексте (может быть длиннее одного ключа). `missingPath.length === 0` —
пара найдена (класс 1); `=== 1` — не хватает только последнего ключа (класс 2, как раньше);
`> 1` — не хватает целой цепочки (новый класс 4). Оба вызывающих места класса 1/2 в
`demo-fireaxe.mjs`/`demo-hazards.mjs`/`demo-comment-insertion.mjs` не изменились и дают те же
диффы — контракт расширен, не сломан.

**Класс 4 (`insertNestedPath`)** — строгое обобщение класса 2, не параллельная ветка кода: при
`missingPath.length === 1` генерирует побайтово ту же строку, что `insertKey` (проверено
равенством строк в `demo-nested-materialization.mjs`, п.3). Точка вставки — та же граница
`range[2]` контейнера, что и в классах 2/3 (issue #14): вставляем после последнего существующего
поля/комментария контейнера, а не после последнего элемента. Каждый уровень отсутствующей
цепочки — отдельная строка `key:` (кроме последней — `key: value`) с отступом на `indentStep`
больше предыдущего уровня. `indentStep = 2` — не предположение: измерено в самой фикстуре на
соседнем реальном пути (`FireAxe.MeleeWeapon.damage → types → Blunt`, шаг ровно 2 между всеми
тремя уровнями, ассерт в `demo-nested-materialization.mjs` п.0), и это та же константа, что уже
принята для отступа тире в `insertComponentBlock` (класс 3, issue #10) — не новое допущение, а
переиспользование уже подтверждённого на реальных файлах шага блочного YAML SS14.

Порядок вложенности — тот, в котором ключи идут в `fieldPath`: каждый следующий уровень **внутри**
предыдущего, ровно как в исходном пути. Ничего другого физически не следует из семантики
YAML-карты, отдельно решать было нечего.

**Аудит `crystall-edge` на другие кандидаты (не только `damage`)** нашёл достаточно случаев
похожей формы, но почти все они — не класс 4, а уже решённый класс 3: у `SpearBone`/`SurvivalKnife`
(`knife.yml`) весь компонент `MeleeWeapon` отсутствует целиком (не только `damage`); у
`ReinforcedShiv`/`PlasmaShiv`/`UraniumShiv` (тот же файл) отсутствует целиком компонент `Fixtures`
(родитель `Shiv` задаёт `fixtures.fix1.{shape,density,mask}` — тоже составной путь, но материализуется
не через класс 4, а через `insertComponentBlock` с многострочным `lines`, ровно как в
`demo-fireaxe.mjs` уже показано на `sound: collection:`); у `CyborgEnergySword` (`e_sword.yml`)
отсутствует `components:` целиком. Ни один из этих случаев не упражняет `insertNestedPath` —
контейнер, внутрь которого материализовать цепочку, в тексте попросту не существует, это другая
задача (класс 3), уже закрытая. Единственная реально найденная форма «компонент есть в тексте,
составное поле внутри него отсутствует целиком» — это исходный `damage` на `FireAxeFlaming`; механика
`insertNestedPath` полю не привязана (работает с любым `fieldPath` над любой уже существующей картой),
но второго независимого поля с этой конкретной формой в форке не нашлось.

### Комментарий перед первым элементом TOP-LEVEL последовательности (`demo-toplevel-seq-comment.mjs`, issue #17)

Резолюция [issue #17](https://github.com/crystallpunk-14/SS14Editor/issues/17) — последний
открытый пункт из раздела выше («Не проверено на реальной фикстуре»). Вопрос: документ каждого
прототипа — сам по себе `YAMLSeq` БЕЗ обёртывающего ключа (в отличие от `components:`, который
это `YAMLSeq` ВНУТРИ карты). Действует ли на нём правило карт («комментарий перед первым
элементом — у контейнера»)?

Полный разбор — [`docs/research/top-level-seq-leading-comment.md`](../docs/research/top-level-seq-leading-comment.md).
Коротко: **нет, не действует — правило для последовательностей ТРЕТЬЕ, более общее.**
Комментарий достаётся ПЕРВОМУ УЗЛУ, которому есть куда его приписать в момент composition:
если контейнер (вложенный список вроде `components:`) уже существует к моменту, когда парсер
видит комментарий, — комментарий достаётся ЕМУ (`componentsSeq.commentBefore`), точно как у
карт (доказано на `fixtures/substation.yml`, `# Core power behavior` перед `Battery`). Но если
контейнера ЕЩЁ НЕТ — самый верх документа, top-level-последовательность прототипов ещё не
существует как узел, пока не встречен первый настоящий токен, — комментарию некуда
приписаться к контейнеру, и он достаётся её первому элементу
(`doc.contents.items[0].commentBefore`), а не `doc.commentBefore` (`null`) и не
`doc.contents.commentBefore` (`undefined`) (доказано на `fixtures/types.yml`).

Это вскрыло не один, а ДВА независимых бага в `deleteSeqItem` для `index===0` — **оба
пофикшены**: (1) «осиротевший отступ» первого элемента ЛЮБОГО вложенного списка (та же болезнь,
что у первого ключа карты, но здесь ломает YAML целиком, не просто дублирует пробелы — см.
`fixtures/substation.yml`); (2) осиротевший комментарий top-level-случая (комментарий остаётся
висеть над новым первым entity вместо того, чтобы уйти вместе со старым — см.
`fixtures/types.yml`). Регрессии нет: `demo-hazards.mjs`, `demo-fireaxe.mjs` и
`demo-comment-insertion.mjs` дают тот же вывод, что и до фикса (единственный прежний вызов
`deleteSeqItem` — `job.yml`, НЕ-первый индекс — не задет ни одним из двух условий).

Для вставки нового первого элемента (симметричный класс правки для класса 2/3) явной функции в
`lib/edits.mjs` нет и не появилось — вопрос чисто информативный до тех пор, пока такой класс
правки не понадобится; разбор фиксирует продуктовую неоднозначность (комментарий — общий
заголовок файла или относится конкретно к старому первому entity?) как открытый вопрос для
будущей реализации, не решает её сейчас.

### Внешняя правка текста, пока инспектор открыт

Не код — архитектурный ответ, т.к. вопрос про процесс, а не про диапазоны:

Инкрементального парсера нет (решение #3 — re-parse на правку, sub-ms на масштабе одного
прототипа), так что источник истины один — текст документа. Перед применением любой
редакторской правки инспектор обязан пере-резолвить путь по ТЕКУЩЕМУ тексту документа
(`vscode.TextDocument.version` как дешёвый маркер: изменился — обязателен re-resolve) и
сверить, что содержимое по вычисленному диапазону всё ещё то, что инспектор в последний раз
показал пользователю. Расхождение → правка отменяется, инспектор форсированно
пересинхронизируется с текста (текст — источник истины, не буфер инспектора). Чтобы не
устроить цикл обратной связи (инспектор пишет правку → событие изменения текста → инспектор
реагирует на своё же изменение → лишний re-render): версия документа ПОСЛЕ
`TextEditor.edit()` известна инспектору заранее (возвращается из промиса) — обработчик
`onDidChangeTextDocument` должен игнорировать событие, чей `document.version` совпадает с
версией, которую инспектор только что сам произвёл.

### Якоря и алиасы

`fixtures/job.yml`: `&icon-rsi` на `JobIconCargoTechnician`, `*icon-rsi` — на
`JobIconShaftMiner` и других. `doc.getIn()`/спуск по пути отдаёт для алиасированного поля
узел типа `Alias` (не `Scalar`) с `.source` — именем якоря. `replaceScalar` явно проверяет
`isAlias()` и отказывает: правка диапазона `*icon-rsi` переписывает только эту ссылку и рвёт
связь с якорем, а НЕ меняет значение везде, где алиас использован — это не то, что ожидал бы
пользователь от «изменить поле». Продуктовое решение зафиксировано прототипом: поле,
резолвящееся в `Alias`, — read-only без явного жеста «открепить от якоря» (материализовать
как независимый скаляр). Сам жест не реализован — не нужен для доказательства тикета.

### `!type:`-теги

`fixtures/light.yml`: `!type:AddZNetworkComponents` хранится как строковое свойство `.tag` на
узле карты, вне диапазона всех вложенных скаляров. Правка соседнего поля
(`CECloudsOverlay.seed`) не задевает строку с тегом — диффнута ровно одна строка,
подтверждено `demo-hazards.mjs`.

### Многострочные и блочные скаляры

`fixtures/memorial.yml`: `description: |`. **Важно:** `range` блочного скаляра включает
индикатор (`|`) и ВСЕ строки содержимого как единый диапазон сырого текста — наивная замена
диапазона голым текстом (как для обычного скаляра) сломает форматирование (потеряется `|`,
слипнутся строки). `replaceBlockScalar` вместо этого: находит заголовок (`|`, `|-`, `>`, …),
переиспользует РЕАЛЬНЫЙ отступ контента (не предполагает 2/4 пробела — читает из текста), и
пересобирает блок с новыми строками на том же отступе.

## Принятые компромиссы прототипа

- ~~Материализация полей поддержана только для контейнера, который уже существует в тексте~~ —
  закрыто в issue #16 (`insertNestedPath`, см. ниже). `findField` больше не кидает ошибку на
  отсутствующем промежуточном ключе.
- `deleteSeqItem`/`deleteMapKey` не параметризованы политикой «оставить комментарий вместо
  удаления вместе с элементом» — продемонстрировано ровно одно поведение (комментарий умирает
  вместе с НЕ-первым элементом; комментарий контейнера переживает удаление первого). Если
  продукту нужна конфигурируемая политика — расширять отсюда, база (точные офсеты) уже есть.
- Стиль/кавычки скаляра при замене не пересчитываются — `replaceScalar` подставляет сырой
  текст как есть. Значения, которым нужна кавычка после замены (например, число превращается
  в строку, начинающуюся с `0`), в прототипе не покрыты.
