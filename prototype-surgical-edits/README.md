# Прототип — выброшенный код (issue #10)

Первоисточник для находок, зафиксированных в резолюции
[issue #10 «Хирургические правки: путь в схеме ↔ диапазон текста»](https://github.com/crystallpunk-14/SS14Editor/issues/10).
Не переносится в продакшн как есть. Библиотека и подход (CST-слой `yaml`@eemeli как оракул
позиций) — по решению [issue #3](https://github.com/crystallpunk-14/SS14Editor/issues/3).

## Что здесь есть

- `lib/model.mjs` — парсинг (`parseDocument` c `keepSourceTokens: true`, `LineCounter`) и
  разрешение пути «entity → компонент по `type:` → поле» в узел AST.
- `lib/edits.mjs` — все три класса правок из тикета плюс удаление ключа/компонента.
- `lib/diff.mjs` — вывод настоящего unified diff (`git diff --no-index`) и re-parse-проверка,
  что результат правки остаётся валидным YAML.
- `demo-fireaxe.mjs` — обязательная часть тикета: три класса правок на реальном
  `fixtures/fireaxe.yml` (1:1 копия `Resources/Prototypes/Entities/Objects/Weapons/Melee/fireaxe.yml`
  форка `crystall-edge`).
- `demo-hazards.mjs` — побочные вопросы карты на реальных фикстурах из того же форка:
  `fixtures/job.yml` (`StatusIcon/job.yml` — якоря/алиасы, комментарий перед НЕ-первым
  элементом списка), `fixtures/light.yml` (`_CE/Procedural/Demiplane/Modifiers/light.yml` —
  `!type:`-тег), `fixtures/memorial.yml` (`Entities/Structures/Furniture/memorial.yml` —
  блочный скаляр `description: |`).

Запуск: `npm install`, затем `node demo-fireaxe.mjs` и `node demo-hazards.mjs`.

## Ответы

### Путь в схеме → диапазон текста

Путь — `{ entityIndex, component, fieldPath }`.

- **Entity** внутри top-level последовательности прототипов адресуется **позиционным
  индексом**. Стабилен на время жизни одного открытого документа: узел дерева инспектора и
  так пересоздаётся целиком при любом внешнем изменении текста (см. ниже), так что индекс не
  «протухает» тише, чем весь документ.
- **Компонент** внутри `components:` адресуется **значением поля `type:`, не индексом**.
  Причины: (1) движок не допускает двух компонентов одного типа на одной entity — `type`
  уже уникальный ключ внутри списка; (2) индекс рассыпается при вставке/удалении СОСЕДНЕГО
  компонента в том же редакторском шаге, а `type` — нет; (3) мерженный (с учётом наследования)
  список компонентов, который видит UI, не обязан совпадать по порядку с сырым списком в
  файле — только `type` согласован по обе стороны.
- **Поле** — обычный спуск по ключам (`fieldPath: string[]`, поддерживает вложенность вроде
  `damage.types.Blunt`).

Разрешение пути даёт либо диапазон существующего скаляра (`node.range` — абсолютные
char-офсеты, `LineCounter.linePos()` переводит в `{line, col}` для `vscode.Range`), либо
контейнер без искомого ключа (см. класс 2).

### Три класса правок (`demo-fireaxe.mjs`, на `fixtures/fireaxe.yml`)

1. **Замена скаляра на месте.** `pair.value.range` — точный диапазон значения без хвостовых
   пробелов/комментариев. Правка — `text.slice(0,start)+new+text.slice(end)`. Диффнута ровно
   одна строка (`Sprite.state: icon → icon-open`).
2. **Материализация унаследованного поля.** У `FireAxeFlaming.MeleeWeapon` в файле нет
   `attackRate` — оно наследуется от родителя. Точка вставки — граница `range[2]` последнего
   существующего поля контейнера: офсет, с которого начинается СЛЕДУЮЩИЙ токен вообще (что бы
   там ни было — соседнее поле, отступ следующего элемента списка), гарантированно вне
   диапазона всех соседей. Отступ — колонка первого соседнего ключа того же контейнера
   (`LineCounter.linePos(...).col`): в блочных картах SS14 все поля одного узла всегда на
   одной колонке. Диффнута ровно одна новая строка.
3. **Добавление целого блока `- type: X` в `components:`.** Тот же приём с `range[2]`
   последнего элемента списка. Отступ считается в двух частях: колонка первого поля первого
   существующего компонента даёт колонку ПОЛЕЙ нового блока; тире — на 2 колонки левее (в
   блочной последовательности `- ` перед первым ключом съедает ровно 2 колонки — эмпирически
   подтверждено на реальном файле, не предположение). Диффнуты ровно три новые строки.

Success-критерий тикета («дифф трогает только целевые строки») выполнен на реальном файле для
всех трёх классов — см. вывод `demo-fireaxe.mjs`. Каждый результат дополнительно проверен
чистым re-parse (`lib/diff.mjs:assertReparsable`) — правка не просто выглядит как чистый diff,
она остаётся валидным YAML.

### Удаление ключа/компонента и «прилипшие» комментарии (`demo-hazards.mjs`)

Нетривиальный и неочевидный факт архитектуры `yaml`@eemeli, обнаруженный эмпирически:
**комментарий перед ПЕРВЫМ элементом коллекции (карты или списка) в CST принадлежит не
элементу, а контейнеру** (`containerNode.commentBefore`), и у первой пары карты `.start`
пуст — даже её собственный отступ на той же строке никому не принадлежит как диапазон.
Для НЕ-первых элементов komментарий/пустые строки/отступ — это `.start`-токены ИМЕННО этого
элемента, с точным офсетом, который эмпирически всегда равен `range[2]` предыдущего соседа
(инвариант проверен и на картах, и на списках, в двух разных файлах).

Отсюда — два разных правила удаления, оба реализованы и продемонстрированы на реальных
файлах:

- **Удаление первого ключа карты** (`typesMap` → `Blunt` в `fixtures/fireaxe.yml`,
  комментарий `# axes are kinda like sharp hammers...` висит на контейнере): комментарий
  остаётся на месте, удаляется только своя строка ключа. Правильная граница начала —
  начало СТРОКИ первого ключа (текстовый откат до последнего `\n`), а не `key.range[0]`:
  голый `key.range[0]` не включает собственный отступ пары, что на реальном прогоне дало
  задвоенный отступ у следующего ключа — баг найден и исправлен именно на этой фикстуре,
  не в вакууме.
- **Удаление НЕ-первого элемента списка** (`fixtures/job.yml`, `# Cargo` перед
  `JobIconCargoTechnician`): комментарий уходит вместе с элементом — `.start[0].offset`
  уже точно указывает на конец предыдущего элемента.

**Не проверено на реальной фикстуре:** комментарий прямо перед САМЫМ первым элементом
последовательности (не карты) — открытый вопрос, нужна отдельная фикстура для карты
(остаётся на карту).

### Внешняя правка текста, пока инспектор открыт

Не код — архитектурный ответ, т.к. вопрос про процесс, а не про диапазоны:

Инкрементального парсера нет (решение #3 — re-parse на правку, sub-ms на масштабе одного
прототипа), так что источник истины один — текст документа. Перед применением любой
редакторской правки инспектор обязан пере-резолвить путь по ТЕКУЩЕМУ тексту документа
(`vscode.TextDocument.version` как дешёвый маркер: изменился — обязателен re-resolve) и
сверить, что содержимое по вычисленному диапазону всё ещё то, что инспектор в последний раз
показал пользователю. Расхождение → правка отменяется, инспектор форсированно
пересинхронизируется с текста (текст — источник истины, не буфер инспектора). Чтобы не
устроить цикл обратной связи (инспектор пишет правку → событие изменения текста → инспектор
реагирует на своё же изменение → лишний re-render): версия документа ПОСЛЕ
`TextEditor.edit()` известна инспектору заранее (возвращается из промиса) — обработчик
`onDidChangeTextDocument` должен игнорировать событие, чей `document.version` совпадает с
версией, которую инспектор только что сам произвёл.

### Якоря и алиасы

`fixtures/job.yml`: `&icon-rsi` на `JobIconCargoTechnician`, `*icon-rsi` — на
`JobIconShaftMiner` и других. `doc.getIn()`/спуск по пути отдаёт для алиасированного поля
узел типа `Alias` (не `Scalar`) с `.source` — именем якоря. `replaceScalar` явно проверяет
`isAlias()` и отказывает: правка диапазона `*icon-rsi` переписывает только эту ссылку и рвёт
связь с якорем, а НЕ меняет значение везде, где алиас использован — это не то, что ожидал бы
пользователь от «изменить поле». Продуктовое решение зафиксировано прототипом: поле,
резолвящееся в `Alias`, — read-only без явного жеста «открепить от якоря» (материализовать
как независимый скаляр). Сам жест не реализован — не нужен для доказательства тикета.

### `!type:`-теги

`fixtures/light.yml`: `!type:AddZNetworkComponents` хранится как строковое свойство `.tag` на
узле карты, вне диапазона всех вложенных скаляров. Правка соседнего поля
(`CECloudsOverlay.seed`) не задевает строку с тегом — диффнута ровно одна строка,
подтверждено `demo-hazards.mjs`.

### Многострочные и блочные скаляры

`fixtures/memorial.yml`: `description: |`. **Важно:** `range` блочного скаляра включает
индикатор (`|`) и ВСЕ строки содержимого как единый диапазон сырого текста — наивная замена
диапазона голым текстом (как для обычного скаляра) сломает форматирование (потеряется `|`,
слипнутся строки). `replaceBlockScalar` вместо этого: находит заголовок (`|`, `|-`, `>`, …),
переиспользует РЕАЛЬНЫЙ отступ контента (не предполагает 2/4 пробела — читает из текста), и
пересобирает блок с новыми строками на том же отступе.

## Принятые компромиссы прототипа

- Материализация полей поддержана только для контейнера, который уже существует в тексте
  (`findField` кидает ошибку, если промежуточный ключ пути отсутствует). Материализация
  ВЛОЖЕННЫХ отсутствующих контейнеров (например, добавить `damage.types.Piercing`, когда в
  файле нет вообще ни `damage`, ни `types`) не реализована — не встретилось в тикете как
  обязательное, но станет нужно для реальных унаследованных полей произвольной глубины.
- `deleteSeqItem`/`deleteMapKey` не параметризованы политикой «оставить комментарий вместо
  удаления вместе с элементом» — продемонстрировано ровно одно поведение (комментарий умирает
  вместе с НЕ-первым элементом; комментарий контейнера переживает удаление первого). Если
  продукту нужна конфигурируемая политика — расширять отсюда, база (точные офсеты) уже есть.
- Стиль/кавычки скаляра при замене не пересчитываются — `replaceScalar` подставляет сырой
  текст как есть. Значения, которым нужна кавычка после замены (например, число превращается
  в строку, начинающуюся с `0`), в прототипе не покрыты.
