# Реестр обработчиков типов: диспетчеризация по FieldKind, а не по FullType

**Статус:** accepted

Инспектору (#9) нужна центральная абстракция — как поле любого C#-типа превращается в виджет и обратно в точечную текстовую правку. Естественный кандидат на ключ диспетчеризации — `FieldMetadata.FullType` (сырое имя C#-типа), уже присутствующий в контракте метаданных (#4). Вместо этого реестр обработчиков ключуется по `FieldKind` — грубой структурной категории, которую вендоренный C#-экстрактор (предшественник `TheShuEd/SS14Editor`, вынесен решением #4) уже вычисляет на этапе экстракции: разворачивает `Nullable<T>`, распознаёт `List<T>`/`Dictionary<K,V>` через интерфейсы, достаёт generic-аргумент из `ProtoId<T>`, ловит `[Flags]`-enum и применяет override `CustomTypeSerializer`. Диспетчеризация по `FullType` потребовала бы повторной реализации этой классификации на TS-стороне. `FullType`/`ProtoTypeArg`/`DataDefinitionType`/`EnumRef` остаются в контракте как полезная нагрузка конкретных обработчиков (например, `object`-обработчик ищет схему по `DataDefinitionType`), а не как ключ поиска.

## Рассмотренные варианты

- **Диспетчеризация по `FullType`** (буквальное прочтение постановки тикета #9). Отвергнут: `FullType` закрытого generic-типа — это `Type.FullName` со всеми аргументами (`List\`1[[System.String]]`), уникальная строка на каждый `T`; обработчик "один на любой `List<T>`" потребовал бы заново разбирать эту строку на TS-стороне вместо переиспользования уже готовой классификации.
- **Единый `switch` по типу в одной функции**, как у предшественника (`controlFor` в `WebUI/js/fields.js`), плюс отдельный `ComponentHandlerRegistry` по имени компонента (не по типу поля) для override отдельных полей (sprite/sound) в обход обычной диспетчеризации. Отвергнут: новый тип добавляется правкой центрального switch, а не независимой регистрацией — прямое нарушение принципа карты «обработчик не привилегирован», применённого не только к `ComponentRegistry`, но и ко всем остальным типам.
- **`Dictionary<FieldKind, Handler>` с типизированным `FieldKind`** (выбран). Каждый обработчик — независимая регистрация под уже вычисленной категорией; составные обработчики (`list`/`map`/`tuple`/`object`/`componentRegistry`) — рядовые записи того же словаря, рекурсивно вызывающие реестр для детей через `Element`/`Key`/`Value`/`TupleElements`.

## Последствия

- Добавление обработчика для нового `FieldKind` (`spriteSpecifier`, `soundSpecifier`, `color`, …) — одна запись в реестре, без изменений в существующих обработчиках или в диспетчере.
- Обработчик отдаёт `render(context) → widget-descriptor` и `apply(interaction) → {range, newText}` — единый примитив для замены значения, вставки нового элемента коллекции (диапазон нулевой ширины) и удаления (диапазон без замены), совпадающий с моделью `WorkspaceEdit`/`TextEdit` VS Code.
- Контейнерные обработчики (`list`/`map`/`tuple`/`object`/`componentRegistry`) реализуются в v1 наравне с примитивами — иначе `components:` целиком осталось бы TODO-заглушкой и v1 не открывал бы ни одного поля ни одного компонента. «Только примитивы» в v1 ограничивает лишь набор **листовых** виджетов (`boolean`/`text`/`integer`/`float`/`enum`).
- Точная форма `widget-descriptor` в протоколе host↔webview (#11) и механика материализации унаследованного значения при жесте «переопределить» (#10) — вне этого ADR, решаются отдельно.
