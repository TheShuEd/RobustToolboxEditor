# Инспектор — сайдбар-панель, не вкладка и не текстовые декорации

**Статус:** accepted

Инспектору (#2) нужна поверхность для рекурсивного редактирования прототипа через примитивные виджеты (чекбокс, dropdown, текстовое поле, кнопка), при этом текстовый редактор обязан оставаться доступным без переключения (ограничение карты) и без ручной настройки сплита пользователем. Рассмотрены три поверхности VS Code API плюс их пересечение с уже запланированными текстовыми провайдерами (автокомплит/hover/go-to-def).

Решение: инспектор — `WebviewViewProvider`, зарегистрированный в сайдбаре (persistent view, не вкладка редактора). Текстовые провайдеры (`registerCompletionItemProvider`/`registerHoverProvider`/`registerDefinitionProvider`) остаются независимой, сосуществующей поверхностью редактирования отдельного поля прямо в YAML — не поглощаются инспектором. Обе поверхности пишут через один и тот же intent-пайплайн `{path, value, range}` → `WorkspaceEdit.replace`, так что состояние не расходится.

## Рассмотренные варианты

- **`TreeView`.** Отвергнут: нет инлайн текстового поля и inline-dropdown, только `checkboxState` (финал в 1.80) — enum и строки/числа деградировали бы до модальных `showQuickPick`/`showInputBox`, что ломает модель рекурсивного инлайн-редактирования.
- **`CustomTextEditorProvider`.** Отвергнут: `priority:"default"` подменяет текстовый редактор для каждого файла-прототипа; `priority:"option"` требует от каждого пользователя вручную сплитить вкладку — конфликт с «без настройки».
- **`WebviewPanel` как несвязанная с документом вкладка**, открываемая по команде. Отвергнут: требует ручного открытия и явного управления lifecycle панели (какой документ она сейчас отражает, что делать при закрытии), тогда как роль инспектора — постоянный компаньон, а не задача, открываемая по случаю. Гибкость размещения (сплит в любую позицию сетки редактора) — реальный плюс этого варианта, но отдельное ОС-окно, которое казалось бы естественным преимуществом вкладки, на десктопе VS Code сегодня недоступно ни одному из вариантов ([microsoft/vscode#14525](https://github.com/microsoft/vscode/issues/14525), [microsoft/vscode#53984](https://github.com/Microsoft/vscode/issues/53984), [microsoft/vscode#213516](https://github.com/microsoft/vscode/issues/213516)) — это не ось различия.
- **Сайдбар (`WebviewViewProvider`).** Принят: persistent, ноль кликов на открытие, не занимает вкладку редактора.

## Последствия

- Нижняя граница `engines.vscode` для v1 — `^1.49` (webview-only не требует `checkboxState`, финализированного лишь в `^1.80`).
- Размещение инспектора ограничено тремя докинг-зонами VS Code (primary sidebar, secondary sidebar, panel) — ни произвольного сплита в сетке редактора, ни отдельного окна.
- Диагностика/валидация (Out of scope v1) должна проектироваться так, чтобы push-модель можно было добавить позже без переписывания intent-пайплайна или реестра обработчиков.
- Из того же вывода следует форм-фактор TS-части CLI-обвязки (#8): бэкенд инспектора физически не может жить в LSP-процессе (`registerWebviewViewProvider`/`postMessage` — API только Extension Host), поэтому расширение в целом остаётся in-process, без отдельного language server. Единственная бесспорная выгода LSP (изоляция тяжёлых операций) достижима дешевле через Node `Worker Thread`; переносимость на другие редакторы и push-диагностика — обе Out of scope.
