# Ленивый поиск путей к ресурсам вместо предпостроенного индекса

**Статус:** accepted

Индекс прототипов (#5) и метаданных (#4) используют eager-построение в фоне с персистентным кэшем — естественная аналогия предполагала тот же паттерн для путей к ресурсам (#7). Проверка предшественника ([`TheShuEd/SS14Editor`](https://github.com/TheShuEd/SS14Editor)) показала: на том же объёме (28777 файлов Textures+Audio) он обходится вовсе без индекса — [`AssetApi.cs`](https://github.com/TheShuEd/SS14Editor/blob/7dcf674b4e5d09b0c5a5bd5fbe309b373e6dce50/src/Api/AssetApi.cs) листингом директории (`Directory.GetDirectories`/`GetFiles`) на каждый запрос автокомплита, без кэша — и это работало на практике.

Решаем искать путь к ресурсу лениво, листингом директории в точке автокомплита, без персистентного индекса и без file watcher (нечего инвалидировать — каждый листинг и так свежий с диска).

## Рассмотренные варианты

- **Eager + персистентный кэш (паттерн #4/#5).** Отвергнут: тот паттерн существует ради дорогого резолва наследования прототипов (~7 с холодный парсинг); для листинга директорий такой цены нет, а инфраструктура кэш-инвалидации (file watcher, mtime-отпечаток) добавляется без реальной необходимости.
- **Ленивый on-demand листинг (паттерн предшественника).** Принят.

## Последствия

Автокомплит в v1 не покрывает `sprite:`/`state:`/`layers:` (сущности) и audio `path:` — эти поля типизированы как `SpriteSpecifier`/`SoundSpecifier` (полиморфные обёртки) либо голым `string` в апстриме, а не `ResPath` напрямую, и диспетчеризация по типу до них не дотягивается независимо от способа хранения. См. резолюцию #7 и «Not yet specified» карты (список исключений по имени поля — будущий тикет).
